# 真实零售数据转换项目：学习路线

实施状态：`planned`。本文件记录待执行计划；规划文档的上传不代表转换、测试或自动化已经完成。

## 目标与范围

使用 UCI Online Retail II 的真实历史交易，先构建一张粒度为 **business_date × country** 的日度分析表，再练习规则维护、增量处理、失败恢复和自动更新。
数据中可识别的取消或冲销记录不等于已结算的现金退款。字段、指标和项目介绍均使用 cancellation/reversal 等与来源证据一致的表达。
历史交易是真实数据；按天送达历史数据属于模拟回放，不能描述为正在接入商家的实时交易。

初始工具：Python、DuckDB SQL、pytest、Git、GitHub。Python 管理来源、批次、执行和检查；SQL 负责清洗、转换与业务聚合。
Snowflake 留到最后的小范围实操；本地 DuckDB 和 GitHub Actions 本身不代表已经获得云数仓实践经验。

## 第一张分析表的约束

- 唯一粒度：`business_date × country`；来源日期的时区含义必须在审计中确认或明确记录为未知。
- 计划字段：销售发票数、已识别购买客户数、销售金额、取消冲销金额、净活动金额、未识别客户销售金额，以及行数与运行追溯字段；金额币种固定 GBP，完整定义见 [BUSINESS_RULES_ZH.md](BUSINESS_RULES_ZH.md)。
- 销售与取消冲销分别计入各自记录的业务日期；净活动金额为当日销售金额减当日取消冲销金额。
- 不把取消冲销自动回配到原订单，不把净活动金额称为利润、现金流或已结算净收入。
- 仅在审计与规则确认后，使用取消标记、数量符号和价格共同分类；冲突记录不得静默归类。
- 国家缺失、客户缺失、零价格和异常数量各有明确处理规则。客户标识缺失不自动意味着国家日度销售不能使用。
- 订单数必须按约定的有效销售发票计算；重复商品行不自动等于重复订单或需要删除的记录。
- 来源真实业务事实与人为测试 fixture 分开存放、标记和展示；测试记录不得混入公开的真实数据汇总。

## 必须保留的工程证据

1. Python 获取、检查、记录批次并执行 SQL 的可复现入口。
2. SQL 从来源到 staging 再到 mart 的清晰依赖关系及业务合同。
3. 样本手算、金额核对、唯一性检查及能发现错误的测试。
4. 一次规则变更的原因、PR 差异、影响说明和反馈修改。
5. 同批重跑、迟到记录、缺失批次、发布失败及补跑的演示记录。
6. 每次运行的输入、输出、状态、业务日期范围和错误定位信息。
7. 自动运行的实际证据，以及明确区分“任务成功”“输出有变化”“来源有新数据”的刷新报告。
