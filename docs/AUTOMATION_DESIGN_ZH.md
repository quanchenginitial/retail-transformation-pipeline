# 自动更新、增量与恢复设计

设计状态：`planned`。本文不包含已运行的流水线，也不启用 GitHub Actions 或定时任务。

## 数据与每日更新的含义

来源是 UCI Online Retail II 的真实历史文件。获取后记录来源、许可、内容校验值和审计结果，并将输入视为不可变。
“每天更新”表示每天开放下一段历史数据进行回放；不是声称原始商家仍在提供新订单。
取消或冲销只代表来源记录中的业务信号，不等同于已结算现金退款。
真实数据产物和人为晚到、更正等 fixture 的产物必须使用不同场景标识，分别运行和展示。

## 两种执行方式

| 方式 / 状态 | 输入与状态 | 计算方法 | 输出 |
|---|---|---|---|
| 阶段 5 本地增量 / planned | 本地不可变批次、持久 DuckDB、已成功批次检查点 | 识别新到记录，重算受影响的日期与国家 | 本地已发布 mart、运行报告与检查点 |
| 阶段 6 云端无状态重建 / planned | 每次校验同一不可变来源、重建批次清单、固定回放配置 | 根据悉尼日期算出 `as_of`，从头读取截至该日应到的全部批次并重建 | 按 run 版本化的汇总 artifact 和运行报告 |

GitHub Actions runner 的本地文件不会被视作下次运行仍存在的数据库。
阶段 6 不依赖上一运行的 DuckDB 或缓存恢复；缓存只可加速下载，命中后仍须核对内容。
本地增量与云端完整重建应在相同输入、场景和规则版本下产生相同结果，便于互相核验。

## 业务时间、到达时间与回放范围

- `business_date`：用于日度国家聚合的交易活动日期。
- `available_date`：该记录在回放场景中允许被系统读到的日期。
- `ingested_at`：本次执行实际读入记录的时间，用于运行追踪。
- 基础真实数据回放可令 `available_date = business_date`；这是假定的到达机制，必须注明。
- 晚到与更正 fixture 显式设定较晚的 `available_date`；不改写不可变真实源文件。
- 构建 staging、客户摘要与 mart 前均限定 `available_date <= as_of`；不能读取未来回放记录补齐当前业务事实。

固定配置计划包含 `historical_start`、`historical_end`、`replay_anchor_sydney_date`、来源校验值和规则版本。
自动执行使用 `Australia/Sydney` 的当前日期；不依赖 runner 默认时区或日期。
每日推进一天：`as_of = min(historical_end, historical_start + 已经过的悉尼日历天数)`。
经过天数从固定的 `replay_anchor_sydney_date` 计算，不从上次任务成功时间计算；跳过运行后仍能确定应处理范围。
回放起点前不生成业务结果；跑完历史区间后报告 `source_exhausted`，不得将重复重建描述为来源新增。
手动补跑可指定受校验的 `as_of`；报告必须记录它与自动推导值的区别。
悉尼日期决定回放进度，不改变来源交易时间本身的时区含义。

## 不可变批次与完整性

计划用确定性规则将来源映射为日期批次，并为每个预期批次记录标识、行数、校验值和场景。
缺失预期文件或清单条目必须失败，不能当成“今天没有交易”。
明确存在、行数为零且校验通过的空批次合法。
同一批次标识出现不同内容必须报错或走显式更正版本，不允许静默覆盖。
人为更正使用独立场景和明确的记录键、版本与到达日期；不把自己生成的键描述成来源提供的 CDC 主键。
阶段 1 要先识别来源实际粒度，不能未经验证把发票号与商品号组合当作唯一行键。

## 阶段 5：本地增量与原子发布

1. 读取待处理批次并核对清单、来源校验值、schema 与可接受日期范围。
2. 基于批次和记录身份识别已处理内容，避免同批重跑重复累计。
3. 计算受影响的 `business_date × country`；在候选区重算其完整结果，而非直接把净额再加一次。
4. 对候选区运行唯一性、分类、金额核对及业务测试。
5. 使用 DuckDB 事务发布受影响结果，并在同一提交边界登记成功批次和检查点。
6. 失败时回滚发布与检查点；另存失败诊断，保留上一版正确业务表。

迟到取消记录影响其自身业务日期；如果更正改变日期或国家，旧分区和新分区都要重算。
增量进度按成功接收的批次或到达序列确定，不能只依赖最大的业务日期。
详细运行日志可独立记录失败，但失败日志不得被解释为成功检查点。

## 阶段 6：CI 与计划执行

计划在 PR 上运行测试和小样本重建；合并后的主分支支持手动及定时完整重建。
定时运行不保证精确到某一分钟，任务时间应留出余量；具体时间、时区处理及配置在实施时验证。
执行顺序：确定 `as_of` → 获取并校验来源 → 检查批次完整性 → staging → mart → 质量检查 → 发布。
同一场景的发布应串行，避免并发运行争抢“最新成功”状态；候选结果以 run 标识隔离。
版本化 artifact 计划包含国家日度汇总、字段版本、来源校验值、`as_of`、Git 提交标识和质量报告。
原始文件、客户级明细、凭据和临时数据库不作为公开成果上传。

只有通过检查的结果才可进入发布步骤；失败诊断使用不同名称，不能冒充业务结果。
“最新成功结果”按同一工作流与场景的已成功运行识别，不以最新上传文件的时间判断。
旧 `as_of` 手动补跑产物保留独立版本，不替换更晚 `as_of` 的 latest；同一 `as_of` 按选定规则版本与代码版本判定，不能只看成功时间。
本次 manifest 记录 `previous_success_run_id` 及其链接；本次失败时继续引用上一成功 run。
artifact 有保留期限；实施时配置足够期限并记录限制，若旧 artifact 已过期，明确报告不可下载，不能承诺永久可用。
版本化 artifact 是运行产物，代码与规则版本由 Git 管理；不在每天运行时把原始数据或数据库提交到仓库。

## 运行报告与验收

计划记录：`run_id`、场景、代码版本、规则版本、来源校验值、起止时间、状态、`as_of`、批次范围、输入/输出行数、金额核对及错误摘要。
刷新报告分别说明任务执行结果、已处理到达日期、最大业务日期、来源是否新增、结果是否改变。
静态来源的文件更新时间或任务成功时间不能被描述为商家数据的新鲜度。

| 场景 / 状态 | 预期结果 |
|---|---|
| 同一批次重复执行 / planned | 行数与业务金额不变，不产生重复记录 |
| 明确空批次 / planned | 正常完成，报告零新增记录 |
| 缺失预期批次 / planned | 失败并指出缺失项，不发布不完整结果 |
| 晚到或更正 fixture / planned | 修正受影响历史分区，结果与同场景完整重建一致 |
| 分类冲突或 schema 异常 / planned | 按合同隔离或失败，不能静默丢弃 |
| 发布前故障 / planned | 旧结果仍可用，本地成功检查点不前移 |
| 跳过一天后恢复 / planned | 从固定锚点推导范围，覆盖漏掉的批次 |
| 历史区间已结束 / planned | 报告 source_exhausted，不声称获得新的真实交易 |
